# 청주 한 바퀴 모바일 UX 개선 제안

- 작성일: 2026-09-22
- 대상: `청주 한 바퀴` 관광 코스 플래너
- 범위: 모바일 화면(우선 360~580px)
- 원칙: 데스크톱 UI의 레이아웃과 시각 표현은 변경하지 않는다.

## 1. 제안 요약

현재 모바일 화면은 데스크톱 콘텐츠를 한 열로 쌓는 방식이라 기능은 모두 사용할 수 있지만, 실제 핵심 과업인 **장소 선택 → 코스 비교 → 선택 코스 확인**까지 스크롤과 탐색 비용이 크다. 모바일에서는 모든 정보를 한꺼번에 보여주기보다 핵심 선택을 먼저 보여주고, 지도와 부가 정보는 필요할 때 펼치는 구조가 적합하다.

우선 다음 5가지를 권장한다.

1. 장소 선택기를 5행 격자에서 가로 스크롤 칩 또는 바텀시트 방식으로 축소한다.
2. 선택한 장소·테마·이동 수단을 모바일 상단에 고정해 현재 조건을 항상 확인하고 바꿀 수 있게 한다.
3. 코스 카드는 모바일 비교에 필요한 `이동시간 / 총 일정 / 방문지 수`를 먼저 보여주고, 선택 즉시 상세로 이어지게 한다.
4. 지도는 기본 축소 요약 + “지도 크게 보기” 방식으로 전환하고, 방문 순서는 세로 타임라인으로 제공한다.
5. 명소·사진 영역의 중복 콘텐츠와 과도한 높이를 줄이고, 터치 환경에서 삭제·업로드 조작을 항상 보이게 한다.

## 2. 현재 화면에서 확인된 모바일 문제

현재 JSX 구조와 반응형 CSS를 기준으로 분석했다. 로컬 환경에 Node/npm 실행기가 없어 브라우저 렌더링 기반 실측은 하지 못했으므로, 실제 구현 단계에서 360px·390px·430px 기기 폭의 시각 회귀 검증이 필요하다.

### 2.1 탐색과 진입

- 580px 이하에서 헤더 내비게이션이 완전히 숨겨진다. 사용자는 상단에서 `코스 찾기`와 `10개 명소`로 바로 이동할 수 없다. (`app/globals.css`의 모바일 미디어 쿼리)
- 히어로 제목의 최소 크기가 2.75rem이고 대시보드 4칸도 각각 최소 140px이라, 첫 핵심 조작인 장소 선택이 첫 화면에서 멀다.
- 히어로의 숫자 대시보드는 소개 정보로는 유용하지만 재방문 사용자의 과업 수행에는 우선순위가 낮다.

### 2.2 장소 선택과 필터

- 장소 선택 버튼 10개가 모바일에서 2열 × 5행, 각 88px 이상으로 표시되어 약 440px 이상의 세로 공간을 차지한다.
- 장소를 바꿀 때마다 테마가 `전체`로 초기화된다. 의도된 동작이라도 사용자에게 초기화 사실이 보이지 않아 필터가 사라진 것처럼 느껴질 수 있다.
- 선택 장소, 테마, 이동 수단이 서로 다른 줄에 놓이고 스크롤 시 사라져 현재 검색 조건을 재확인하거나 바꾸려면 위로 돌아가야 한다.
- 일부 라벨이 약 0.68~0.78rem로 작아 야외 관광 상황이나 고령 사용자의 가독성이 떨어질 수 있다.

### 2.3 코스 결과, 지도, 상세의 연결

- 모바일에서도 코스 결과 영역에 최대 높이 560px과 내부 세로 스크롤이 적용된다. 페이지 스크롤 안에 목록 스크롤이 생겨 스크롤 주체가 헷갈릴 수 있다.
- 결과 목록 다음에 최소 430px 지도와 상세가 이어져, 코스를 선택해도 선택 결과의 핵심 내용까지 이동 거리가 길다.
- 지도 SVG는 680 × 500 좌표계를 작은 화면에 축소한다. 라벨과 핀이 함께 작아지고, SVG 핀 자체에는 모바일 권장 수준의 독립적인 터치 영역이 보장되지 않는다.
- 상세 방문 순서가 가로 스크롤 목록이다. 가로 스크롤 가능 여부가 드러나지 않으며, 긴 코스의 전체 순서를 한눈에 파악하기 어렵다.
- 지도 선택과 장소 선택이 연결돼 있지만, 지도를 눌렀을 때 코스·테마까지 바뀔 수 있어 사용자가 맥락 변화를 놓칠 수 있다.

### 2.4 명소와 사진

- 명소 카드 10개가 모바일에서 한 열로 쌓여 카드 목록만 최소 약 1,400px가 된다. 상단의 장소 선택기와 사실상 같은 선택 기능을 반복한다.
- 명소 상세 제목은 최소 2.6rem이라 `국립현대미술관 청주`처럼 긴 이름에서 줄바꿈 비중이 지나치게 커질 수 있다.
- 사진 영역은 최소 높이 580px이고 5개 슬롯을 항상 노출해 사진이 적을 때 빈 공간이 크다.
- 사진 삭제 버튼은 기본 `opacity: 0`이고 hover/focus 때만 보인다. hover가 없는 터치 기기에서는 삭제 기능 발견성이 낮다.
- 빈 사진 슬롯 여러 개가 모두 같은 파일 선택 동작을 수행하여, 서로 다른 기능처럼 보이지만 결과는 동일하다.

### 2.5 모바일 접근성과 환경 대응

- 작은 아이콘 버튼과 SVG 핀에 최소 44 × 44px 터치 영역이 일관되게 적용되지 않았다.
- hover 상태는 정의되어 있으나 전역 `:focus-visible` 표현이 충분하지 않다.
- 하단 홈 인디케이터가 있는 기기를 위한 `env(safe-area-inset-bottom)` 여백 정책이 없다.
- 업로드 성공·실패 메시지는 `aria-live`가 적용돼 있으나, 업로드 중 진행 상태와 삭제 중 상태가 개별 항목에서 충분히 전달되지는 않는다.

## 3. 목표와 비목표

### 목표

- 첫 진입 후 핵심 장소 선택까지 한 화면 또는 1회 이내 스크롤로 도달한다.
- 장소 선택 후 추천 코스와 핵심 비교 지표가 즉시 보인다.
- 지도보다 방문 순서와 예상 시간이 먼저 이해되게 한다.
- 모든 주요 조작을 한 손으로 수행할 수 있고 터치 목표를 최소 44 × 44px로 맞춘다.
- 긴 페이지와 중첩 스크롤을 줄인다.
- 360px에서도 가로 페이지 스크롤이 발생하지 않게 한다.

### 비목표

- 데스크톱 레이아웃, 크기, 색상, 상호작용을 재설계하지 않는다.
- 코스 추천 로직이나 여행 데이터 자체를 변경하지 않는다.
- 현재 개념 지도를 실제 지도 서비스로 교체하지 않는다.
- 사진 API 및 서버 저장 구조를 변경하지 않는다.

## 4. 권장 모바일 정보 구조

모바일에서는 아래 순서로 재구성한다.

1. 축약 헤더: 브랜드 + `코스` / `명소` 메뉴 버튼
2. 축약 히어로: 핵심 문장 + `코스 찾기` CTA
3. 장소 선택: 현재 장소 + 가로 스크롤 칩 또는 전체 목록 바텀시트
4. 고정 조건 바: 테마 + 도보/자동차 + 결과 수
5. 추천 코스 카드 목록
6. 선택 코스 요약: 제목, 핵심 수치, 세로 방문 순서
7. 접을 수 있는 개념 지도
8. 명소 상세: 현재 명소 1개 중심
9. 사진 갤러리
10. 푸터

이 구조의 핵심은 **선택과 비교를 먼저, 공간을 많이 차지하는 지도와 부가 설명은 그다음**에 배치하는 것이다.

## 5. 화면별 개선안

### 5.1 헤더와 히어로

#### 제안

- 숨겨진 내비게이션을 모바일 전용 메뉴 버튼으로 대체한다. 눌렀을 때 `코스 찾기`, `10개 명소` 두 앵커를 작은 팝오버 또는 시트로 제공한다.
- 히어로 제목을 2.25~2.6rem 범위로 줄이고 강제 `<br>`은 모바일에서 무효화해 자연스럽게 줄바꿈한다.
- 본문 설명은 최대 3~4줄 수준을 유지하고, CTA는 폭 100%·최소 높이 48px로 만든다.
- 숫자 대시보드는 모바일에서 3개 핵심 수치를 한 줄 요약으로 축약하고, 설명용 네 번째 칸은 숨기거나 접는다.

#### 기대 효과

- 첫 화면에서 서비스 목적과 다음 행동을 바로 이해할 수 있다.
- 장소 선택 영역까지 도달하는 스크롤 거리가 줄어든다.

### 5.2 장소 선택기

#### 1안: 가로 스크롤 칩 — 우선 권장

- `01 무심천`, `02 용화사`처럼 번호 + 짧은 이름만 담은 칩을 한 줄로 제공한다.
- 선택 칩은 기존 노란색을 유지하고, 좌우 끝에 콘텐츠가 일부 보이도록 해 가로 스크롤 가능성을 암시한다.
- `전체 장소` 버튼을 마지막에 배치해 바텀시트 목록을 열 수 있게 한다.
- 스크롤 스냅을 보조적으로 사용하되 사용자의 자유 스크롤을 막지는 않는다.

#### 2안: 현재 장소 + 바텀시트

- 화면에는 현재 선택 장소만 큰 버튼으로 노출한다.
- 버튼을 누르면 10개 장소를 2열 목록으로 보여주는 바텀시트를 연다.
- 높이는 줄지만 한 번 더 눌러야 하므로, 빠른 비교가 중요한 현재 서비스에는 1안을 우선한다.

#### 상태 처리

- 장소 변경 시 테마 초기화를 유지한다면 “장소가 바뀌어 테마를 전체로 재설정했어요”를 짧게 안내한다.
- 가능하면 사용자가 고른 테마가 새 장소에서도 결과를 갖는 경우에는 유지하고, 결과가 없을 때만 `전체`로 되돌린다.

### 5.3 조건 바와 결과 목록

#### 제안

- 장소 선택기 아래의 조건 바를 모바일에서 `position: sticky`로 제공한다. 사이트 헤더를 고정하지 않는다면 `top: 0`, 고정한다면 헤더 높이만큼 offset을 둔다.
- 1행에는 현재 장소와 결과 수, 2행에는 테마 셀렉트와 도보/자동차 세그먼트를 배치한다.
- 내부 목록 스크롤을 제거하고 페이지 스크롤 하나만 사용한다.
- 코스 카드는 다음 순서로 단순화한다.
  - 첫 줄: 테마 배지 + 코스명
  - 둘째 줄: 선택 이동수단 시간(가장 강조) + 권장 전체 일정 + 방문지 수
  - 셋째 줄: 방문지 이름, 최대 2줄 후 생략
- 카드를 누르면 선택 상태만 바꾸는 데 그치지 않고, 바로 아래 선택 코스 요약으로 부드럽게 이동시키거나 카드 자체를 확장한다.
- 결과가 많을 경우 처음 3개만 보여주고 `나머지 N개 보기`를 제공한다.

#### 권장 문구

- `도보 42분 · 전체 3시간 30분 · 3곳`
- `이 코스 자세히 보기`
- 빈 결과: `이 장소에는 예술 테마 코스가 없어요.` + `전체 테마 보기`

### 5.4 선택 코스 상세와 지도

#### 제안

- 모바일에서는 상세 제목과 핵심 수치를 지도보다 먼저 표시한다.
- 방문 순서를 가로 목록에서 세로 타임라인으로 바꾼다. 각 단계는 번호, 장소명, 카테고리만 우선 노출하고 긴 설명은 생략한다.
- 지도는 초기에는 약 220~280px 높이의 미리보기로 표시한다.
- `지도 크게 보기` 버튼을 누르면 전체 화면 다이얼로그 또는 바텀시트에서 지도를 제공한다.
- 지도 핀의 시각 크기와 별도로 투명한 터치 영역을 최소 44px로 확보한다.
- 작은 화면에서는 전체 10개 장소 라벨 대신 현재 코스의 정류지만 라벨링해 겹침을 줄인다.
- 지도에서 다른 장소를 선택하면 `장소를 바꾸고 추천 코스를 다시 볼까요?`처럼 상태 변화가 크다는 점을 명확히 하거나, 지도 핀은 정보 확인만 하도록 역할을 제한한다.

#### 이유

현재 지도는 실제 길찾기 지도가 아니라 개념도다. 모바일에서는 정확한 공간 탐색보다 코스 순서와 시간 비교가 더 중요한 정보이므로, 텍스트 타임라인을 주 정보로 두는 편이 이해와 접근성에 유리하다.

### 5.5 명소 목록과 상세

#### 제안

- 10개 대형 카드를 다시 한 열로 나열하지 않고, 장소 선택기와 동일한 가로 칩을 재사용한다.
- 현재 명소 1개의 상세만 보여주고 좌우 `이전 명소` / `다음 명소` 버튼을 제공한다.
- 제목은 `clamp(2rem, 10vw, 2.6rem)` 수준으로 제한하고 긴 이름은 2줄까지 허용한다.
- 주소 행은 아이콘을 `flex-shrink: 0`으로 고정하고 텍스트가 자연스럽게 여러 줄이 되게 한다.
- 설명이 길다면 첫 3~4줄 뒤 `설명 더 보기`를 제공한다.
- 출처 링크는 최소 높이 44px의 명확한 보조 버튼으로 만든다.

### 5.6 사진 갤러리

#### 제안

- 빈 슬롯 5개를 모두 표시하지 않고 `사진 추가` 타일 1개와 `N장 더 추가 가능` 안내만 제공한다.
- 사진은 2열 격자 또는 가로 스크롤 카드로 보여주되, 사진 수에 맞춰 영역 높이가 자연스럽게 늘어나게 한다. 고정 최소 높이 580px는 제거한다.
- 터치 기기에서는 삭제 버튼을 항상 표시한다. 데스크톱의 hover 동작은 유지한다.
- 삭제 전 확인은 브라우저 기본 confirm보다 사진 미리보기와 함께 보이는 모바일 다이얼로그를 권장한다.
- 업로드 중에는 추가 버튼 내부에 진행 상태를 표시하고 중복 탭을 막는다.
- 업로드 오류 메시지는 입력 버튼 가까이에 표시하고 재시도 행동을 함께 제공한다.

## 6. 모바일 전용 시각·상호작용 기준

| 항목 | 권장 기준 |
|---|---|
| 적용 폭 | 우선 `@media (max-width: 580px)` 안에서만 적용 |
| 좌우 여백 | 16px, 360px 화면에서는 최소 14px |
| 주요 터치 영역 | 최소 44 × 44px |
| 주요 버튼 높이 | 48~52px |
| 본문 글자 | 16px 이상 |
| 보조 글자 | 원칙적으로 12px 이상, 핵심 정보는 14px 이상 |
| 카드 간격 | 10~12px |
| 섹션 간격 | 48~64px |
| 고정 바 | 배경 불투명도 확보, 1px 구분선, `z-index` 명시 |
| 하단 여백 | `padding-bottom: calc(기본값 + env(safe-area-inset-bottom))` |
| 모션 | 기존 `prefers-reduced-motion` 정책 유지 |

## 7. 데스크톱 UI를 보존하는 구현 원칙

1. 기존 기본 스타일과 821px 이상 레이아웃은 수정하지 않는다.
2. 시각 변경은 우선 `@media (max-width: 580px)`에만 추가한다.
3. 모바일 전용 요소는 `.mobile-only`, 데스크톱 전용 요소는 `.desktop-only`처럼 명시적으로 구분한다.
4. 동일 데이터를 렌더링하는 프레젠테이션 컴포넌트만 분리하고, 코스 선택 상태와 필터 로직은 공유한다.
5. 화면 폭을 JavaScript로 읽어 분기하지 않는다. CSS 미디어 쿼리를 우선 사용해 hydration 불일치를 피한다.
6. DOM 순서를 바꿔야 할 때는 접근성 읽기 순서가 시각 순서와 일치하도록 한다. CSS `order`만으로 큰 구조를 뒤집지 않는다.
7. 터치 전용 스타일은 필요할 경우 `@media (hover: none) and (pointer: coarse)`로 제한한다.
8. 구현 전후 데스크톱 1280px·1440px 스크린샷을 비교해 시각 회귀가 없음을 확인한다.

## 10. 완료 기준과 검증 체크리스트

### 기능

- [ ] 장소를 선택하면 관련 코스 목록과 결과 수가 즉시 갱신된다.
- [ ] 테마·이동 수단을 바꾸면 카드의 시간과 결과가 올바르게 바뀐다.
- [ ] 코스 선택 후 제목, 이동시간, 방문 순서가 같은 코스를 가리킨다.
- [ ] 사진 추가·새로고침·삭제를 터치만으로 발견하고 실행할 수 있다.
- [ ] 빈 결과에서 전체 테마로 정상 복귀한다.

### 모바일 레이아웃

- [ ] 360px, 390px, 430px, 580px 폭에서 가로 페이지 스크롤이 없다.
- [ ] 화면 내부에 의도하지 않은 중첩 세로 스크롤이 없다.
- [ ] sticky 조건 바가 콘텐츠나 팝오버를 가리지 않는다.
- [ ] 긴 장소명과 주소가 잘리지 않고 최대 2~3줄 안에서 읽힌다.
- [ ] 키보드가 열린 상태에서도 셀렉트·업로드 조작이 가능하다.
- [ ] iOS Safari와 Android Chrome에서 safe-area와 sticky 동작을 확인한다.

### 접근성

- [ ] 주요 조작의 터치 영역이 최소 44 × 44px다.
- [ ] 선택 상태가 색상뿐 아니라 텍스트 또는 `aria-pressed`로 전달된다.
- [ ] 포커스 표시가 배경과 충분한 대비를 갖는다.
- [ ] 지도 없이도 방문 순서와 코스 정보를 모두 이해할 수 있다.
- [ ] 200% 확대에서도 핵심 기능이 잘리거나 겹치지 않는다.
- [ ] 모션 감소 설정에서 자동 스크롤 및 지도 애니메이션을 최소화한다.

### 데스크톱 회귀 방지

- [ ] 1280px와 1440px에서 기존 헤더, 히어로, 5열 선택기, 2열 플래너, 명소 카드 배치가 유지된다.
- [ ] 데스크톱 hover 상태와 지도/사진 갤러리 상호작용이 유지된다.
- [ ] 모바일 전용 요소가 581px 이상에서 노출되지 않는다.

## 11. 권장 진행 순서

1. P0 항목을 하나의 모바일 UX 개선 작업으로 구현한다.
2. 360/390/430/580px에서 핵심 과업을 수동 검증한다.
3. 1280/1440px 데스크톱 시각 회귀를 확인한다.
4. 실제 사용자 3~5명에게 “무심천이 포함된 도보 코스 찾기” 과업을 수행하게 한다.
5. 장소 선택부터 코스 상세 확인까지의 탭 수, 소요 시간, 되돌아간 횟수를 기록한다.
6. 검증 결과에 따라 P1의 지도 확장 방식과 명소 탐색 방식을 확정한다.

가장 먼저 구현할 조합은 **가로 장소 칩 + sticky 조건 바 + 간결한 코스 카드 + 세로 방문 타임라인**이다. 이 네 가지가 현재 기능을 유지하면서 모바일의 스크롤 부담과 선택 맥락 손실을 가장 크게 줄인다.
